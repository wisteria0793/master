# フェーズ3 実装と改善の振り返り

本セクションでは、フェーズ3の観光ルート推薦におけるルールベースのアプローチ実装と、景観クラスタの特定ロジックの改善についてまとめます。

## 1. ルールベース推薦の実装
教員からのアドバイスに基づき、GNNで統合した「ブラックボックスな地区」を直接使うのではなく、**「機能」と「景観」それぞれのモダリティを直接条件として指定する** アプローチへ移行しました。

- **起点POIの条件抽出**: 起点として選ばれたPOIの「POIクラスタ（機能）」と「景観クラスタ」を取得し、両方の条件が一致するPOIのみを推薦候補として抽出。
- **景観重視のルート生成**: 抽出されたPOIを巡る際、起点と同じ景観クラスタの重みをNetwork KDEによって道路上に伝播させ、その景観コストを用いたTSPでルートを生成。

## 2. 景観データの修正 (GNN単体平滑化結果の採用)
当初は GNNで「POIと統合」された出力結果を参照していましたが、景観の純粋な空間的な滑らかさを保証するため、**「景観データ単体でGNN平滑化を行い、K=12でクラスタリングした結果 (`smoothed_landscape_map_k12.html` 相当)」** を使用するようにスクリプト全体を修正しました。

## 3. 景観クラスタ特定ロジックの改善 (Radius-based Distance-weighted Voting)
POIがどの景観クラスタに属しているかを判定する際、単一のノイズ地点に引っ張られず、かつ面的な広がりを正しく考慮できるロジックを導入しました。

### 採用アルゴリズム: 半径ベースの距離重み付き投票
- **半径内のポイント取得**: 緯度経度をメートル近似に変換し、KDTreeを用いてPOIから **半径150m以内** の景観ポイントをすべて取得。
- **重み付き投票**: 単純な多数決だと大きなクラスタに飲み込まれてしまうため、**「POIからの距離の逆数」** を重みとして各クラスタのスコアを加算。
- **結果**: このアルゴリズムにより、POIのすぐ近くにある局所的な小さなクラスタを正しく評価しつつ、周囲の空間的な広がりも考慮した堅牢なクラスタ決定が可能になりました。

### 不整合の解消
推薦エンジン側で計算された景観クラスタと、ルーター（Network KDE）側で計算される景観クラスタがズレないよう、`router.py` が推薦エンジンの計算結果を直接受け取って適用するようにパイプラインを修正しました。

## 4. 可視化マップの分離出力
分析のしやすさを向上させるため、`visualize_all_clusters.py` を修正し、レイヤーを1つのファイルに重ねるのではなく以下の2つの独立したHTMLとして出力するように変更しました。
- `docs/results/visualize_landscape_clusters.html` (GNN景観単体)
- `docs/results/visualize_poi_clusters.html` (POI機能単体)
