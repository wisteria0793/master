# 観光ルート推薦プロトタイプ アルゴリズム詳細仕様書

**作成日:** 2026年4月9日  
**最終更新日:** 2026年4月9日

本ドキュメントでは、現在実装されているプロトタイプシステム（`src/urban_analysis/prototype/`）において、どのようにデータが処理され、POIが推薦され、最終的な観光ルートが生成されるのか、その背後にあるアルゴリズムや計算式を網羅的に解説します。

## 1. データの準備とクラスタ割り当て (`data_loader.py`)

プロトタイプでは、まず各観光施設（POI）に「景観の特性（クラスタ）」と「テキストの特徴（ベクトル）」を付与します。その際、ノイズとなるデータを事前に除外しています。

### 1.1. POIの事前フィルタリング (ノイズ除外)
データの読み込み段階で、施設名に `閉店`, `休業`, `休館` などのキーワードが含まれているものを自動的に除外します。これにより、実在しない施設がルートに組み込まれることを防ぎます。除外されたPOIに対応するテキストベクトルも同時に削除されます。

### 1.2. 景観クラスタリング
道路上の50m間隔の地点（Street View取得地点）における統合特徴量ベクトル（StreetCLIPによる画像特徴 + GNNによる道路網の構造的特徴）に対し、**階層的クラスタリング（ウォード法）**を実行し、全地点を20個のクラスタに分類します。

### 1.3. POIへの景観クラスタの紐付け (K近傍法による多数決)
POI自体は画像や道路網の情報を持たないため、周辺の景観情報から特性を付与します。
- POIの座標と、Street View地点の座標をラジアンに変換します。
- `scipy.spatial.KDTree` を用いて、各POIから**物理的距離が近い上位5つのStreet View地点 (K=5)** を検索します。
- 取得した5地点の中で**最も多く出現したクラスタ番号（最頻値）**を、そのPOIの「景観クラスタ」として割り当てます。
これにより、局所的なノイズを排除し、POI周辺の「面的な景観のまとまり」を抽出します。

### 1.4. テキストベクトルの付与
施設紹介文を `Sentence-BERT` でベクトル化したデータ（`facility_embeddings.npy`）を読み込み、各POIに付与します。これは後続のPOI推薦のみに使用されます。

## 2. 推薦ロジック (`recommender.py`)

基準となるPOI（起点）が指定された際、次に訪れるべきPOI候補を、テキストの意味的関連性に基づいて純粋に抽出します。

### 2.1. 距離フィルタリング (Haversine距離)
起点の座標から各POIまでの球面距離を**Haversine法**で計算し、直線距離で指定閾値（デフォルト：3,000m）以内のPOIのみを候補として残します。

### 2.2. 類似度スコアリング
起点POIと候補POIの `Sentence-BERT` ベクトル間の**コサイン類似度**を計算します。類似度が高い順にソートし、上位N件（デフォルト：10件）を推薦POIとして決定します。これにより、「何を見るか（施設の意味や機能）」という純粋な目的ベースでの推薦が行われます。

---

## 3. 経路探索と最適化 (`router.py`)

推薦されたPOI群（起点 + 10件 = 計11地点）を巡る、景観を考慮した最適なルートを計算します。

### 3.1. 道路ネットワークグラフの準備
OpenStreetMap (OSM) データから構築した歩行者用道路ネットワークグラフ (`.graphml`) を読み込みます。計算コスト削減のため、全11地点が含まれる最小のバウンディングボックス（+余白）でグラフを切り出します。

### 3.2. Network KDE (カーネル密度推定) による景観スコアの算出
単なる最短距離ではなく、「起点と同じ景観要素が多い道」を優先的に通るための処理です。
1. **イベントノードの特定**: サブグラフ内で、起点POIと「同じ景観クラスタ」に属するStreet View地点をイベント（熱源）として抽出します。
2. **密度の伝播 (Dijkstra法)**: 各イベントノードから、ネットワークに沿って周囲の道路（ノード）へ密度を伝播させます。距離 `dist` が離れるほど影響力が減衰するQuartic（四次）カーネルを使用します（上限デフォルト500m）。
   `kernel_val = (1 - (dist / KDE_BANDWIDTH_M)^2)^2`
3. **エッジ（道路）密度の算出**: 道路の両端ノードの密度を平均し、道路の長さで割ることで、その道路セグメントの「景観密度 (`density`)」とします。

### 3.3. 景観コスト関数の適用
算出した景観密度を用いて、各道路（エッジ）の通過コストを以下のように再定義します。
`kde_cost = 物理的距離 (length) / (1.0 + KDE_ALPHA * density)`
`KDE_ALPHA`（デフォルト: 10.0）が効くことで、**景観密度が高い道ほどコストが劇的に下がり**、アルゴリズムに選ばれやすくなります。

### 3.4. 移動コスト行列の作成
上記の `kde_cost` を重みとして用いて、Dijkstra法により11個のPOIすべての組み合わせ間の移動コストを計算し、コスト行列を作成します。

### 3.5. TSP (巡回セールスマン問題) の厳密解法
**動的計画法 (Held-Karpアルゴリズム)** を用いて、起点からスタートし全ての推薦POIを巡る、総景観コストが最小となる最適な訪問順序を計算します。

### 3.6. 経路ジオメトリの生成
決定した最適順序に従い、地点間を再び Dijkstra法 (`kde_cost`ベース) で繋ぎ合わせ、地図上に描画するための詳細なルート座標リスト（PolyLine）を生成します。

---

## 4. 可視化 (`run_prototype.py`)

`Folium` を用いて、計算結果をHTMLのインタラクティブマップとして出力します。TSPで決定された**実際の訪問順序**に従って地図上のマーカーに番号を振り、ルート線と不整合が起きないように描画します。

## 5. 変更履歴とアルゴリズムの変遷

### 2026/04/09 のアップデートにおける主な変更点と理由

システムの役割分担（POI選定は「内側の意味」、ルート探索は「外側の景観」）を明確にし、ノイズへの耐性を高めるため、以下のアップデートを行いました。

1. **POIへの景観クラスタ紐付けの改善 (K=5 多数決)**
   - **以前**: 最も物理的距離が近い「1つのStreet View地点」のクラスタをそのままPOIのクラスタとして採用（Nearest Neighbor）。
   - **課題**: たまたまその1点だけ特殊な景観が写り込んでいる「ノイズ点」であった場合、POI全体が誤った特性として分類され、面的なエリアの雰囲気を捉えきれていなかった。
   - **変更後**: 近傍の5点 (K=5) を取得し、その中で最も多いクラスタを採用する多数決方式（KNN）に変更。これにより、局所的なノイズに引っ張られず、より安定して「面的な景観特性」をPOIに紐付けられるようになった。
2. **ノイズPOIの事前フィルタリング導入**
   - **課題**: 閉店や休館している施設が推薦結果に混ざり、ルートの信頼性を損なっていた。
   - **変更後**: 施設名に「閉店」「休業」などのキーワードが含まれるPOIをデータロード時に除外する処理を追加。
3. **推薦ロジックからの景観バイアスの排除**
   - **以前**: Sentence-BERTの類似度スコアに対し、起点と「景観クラスタが一致」する場合に `+0.1` のボーナスを加算してPOIを推薦していた。
   - **課題**: 目的の施設を選ぶ段階で景観が混ざると、「何を見るか」という検索システムとしての役割がブレてしまう。
   - **変更後**: ボーナス加算を完全に廃止し、推薦（目的地選び）は純粋に施設紹介文のベクトル類似度のみで行うように変更。「何を見るか」はテキスト類似度で決定し、「どういう雰囲気の道を通るか」はNetwork KDEを用いた経路探索のみに任せるという明確な役割分担を実現した。
